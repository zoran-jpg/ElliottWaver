# Real Market Data Validation (RMDV) Concept

## Scope and Constraints

This document defines a local-first validation concept for market data quality and reproducible analysis behavior.

Constraints:
- Local first only.
- No downloads.
- No API access.
- No database usage.
- No new dependencies.

This concept is implementation-agnostic and designed to be integrated into the existing ElliottWaver workflow.

## Data Domain Separation

Synthetic and real OHLCV data must be treated as separate domains.

- Synthetic domain:
  - Purpose: controlled scenario generation and deterministic stress testing.
  - Labeling: always marked as synthetic.
  - Availability metadata: can be simulated, but never claimed as historically observed.

- Real domain:
  - Purpose: historical behavior validation under realistic market conditions.
  - Labeling: always marked as real.
  - Availability metadata: must distinguish observed facts from assumptions.

Rule:
- No mixed dataset may hide source boundaries. If synthetic and real rows are combined for experiments, each row remains source-labeled and each result must carry a domain composition summary.

## Availability-Time Classification (Independent Axis)

Availability times are classified independently from OHLCV correctness:

- proven:
  - Availability time is evidenced by locally stored records or deterministic export logs.
  - Evidence link is documented in the dataset manifest.

- simulated:
  - Availability time is generated by an explicit simulation model.
  - Simulation method and parameters are documented.

- unknown:
  - Availability time cannot be evidenced and is not simulated.
  - No causal claims are allowed for unknown availability.

Hard rule:
- No invented historical availability timestamps. Unknown stays unknown.
- Export timestamp alone is not evidence of historical data availability.

## Required Dataset Metadata (Manifest)

Each dataset (or immutable export slice) must include at minimum:

- origin/source description
- instrument type
- symbol
- timeframe
- timezone normalization statement (UTC)
- export timestamp (UTC)
- license information
- SHA256 digest of raw input artifact

Recommended local manifest fields:

- dataset_id
- data_domain: synthetic | real
- availability_classification: proven | simulated | unknown
- row_count
- first_candle_open_utc
- last_candle_open_utc
- sha256_raw_file
- sha256_normalized_file
- generated_by (local tool or script name)
- generation_parameters (for synthetic/simulated availability)

## Validation Layers

Validation is split into orthogonal layers.

### Layer 1: OHLCV Structural Integrity

Checks:
- required columns present: timestamp, open, high, low, close, volume
- numeric fields parseable
- timestamp parseable and UTC-normalized
- monotonic candle order by timestamp
- intra-row constraints: high >= max(open, close), low <= min(open, close), high >= low
- volume non-negative according to instrument conventions

### Layer 2: Duplicate and Gap Validation

Checks:
- duplicate candles by key (symbol, timeframe, timestamp)
- conflicting duplicates (same key with different values)
- missing intervals based on timeframe cadence
- gap segmentation report (short/long gaps)

### Layer 3: Trading Session Coherence

Checks:
- session boundaries consistent with market type
- expected inactive windows vs observed bars
- suspicious out-of-session bars flagged for review

This layer is profile-driven and must be explicit per instrument class.

## Reproducibility and Fixed as_of Runs

Validation and downstream analysis must support fixed as_of reference runs.

Requirements:
- as_of is always UTC.
- identical input artifacts + identical config + identical as_of -> identical outputs.
- outputs include run metadata with digests and timestamps.

Run record fields:
- run_id
- as_of_utc
- dataset_id
- dataset_sha256
- validation_profile
- result_sha256
- created_at_utc
- commit_sha
- config_digest_sha256
- tool_versions

Result hash rule:
- `result_sha256` must be computed from deterministic result content only.
- Variable runtime metadata (wall-clock start/end, host-specific paths, process IDs, random seeds unless fixed) must be excluded from the hashed payload.

## Geometric vs Causal Validation Separation

Validation domains must stay separate:

- geometric validation:
  - checks shape properties (pivot geometry, swing consistency, wave proportions, pattern constraints)
  - ignores causality assumptions unless explicitly requested

- causal validation:
  - checks time-availability constraints (what was knowable at as_of)
  - enforces availability classifications and causal cutoffs

Rule:
- Geometric pass does not imply causal pass.
- Causal pass does not imply geometric quality.

## Scenario Matrix for Validation Coverage

Synthetic and real data should both be evaluated across scenario classes:

- trend up
- trend down
- sideways/range
- high volatility
- low volatility
- trend regime change

Each scenario should provide:
- expected behavior notes
- minimum sample window length
- acceptance criteria for geometric and causal layers

## Reference Markets (Proposal)

Proposed reference markets for local validation packs:

- BTC (crypto)
- ETH (crypto)
- Gold (commodity)
- WTI (commodity)
- NVDA (equity)

These are proposals for coverage diversity and should be represented across multiple timeframes where local data already exists.

## Integration Roadmap (Conceptual)

RMDV outputs are intended to feed later stages:

- Elliott analysis validation
- Fibonacci projection validation
- indicator pipeline validation
- backtesting input quality gates

Integration principle:
- Data quality and availability provenance are validated first, then consumed by analytical modules.

## Local Implementation Pattern

Suggested local folder convention:

- engineering/rmdv/
  - manifests/
  - profiles/
  - reports/
  - runs/

No external service dependency is required for this concept. All artifacts are local files with explicit SHA256 digests.

## Governance Notes

- No mutation of source historical artifacts during validation.
- Every normalization step produces a new artifact with a new digest.
- Any assumption must be machine-readable and reviewable.
- Unknown availability remains unknown unless evidence is added.

This concept is ready for phased implementation in subsequent engineering packages without requiring architecture changes or external infrastructure.

## EP12 Schema and Concept-Code Clarifications

- Normalized dataset schema must stay aligned with EP12 temporal normalization guarantees.
- Provenance and availability classifications are recorded as validation metadata and must not silently alter normalized OHLCV payload semantics.
- Any concept-level pseudo-code or illustrative formulas in this document are visual/functional references only.
